الخدمات الخارجية التي يستخدمها المشروع فعليًا:

  الخدمة        | الاستخدام                                         | إلزامية؟
  --------------|---------------------------------------------------|---------------------------
  Supabase      | قاعدة بيانات PostgreSQL + جدولة المهام (pg_cron)   | قاعدة البيانات: إلزامية
                |                                                   | Cron: موصى به بشدة
  Render        | استضافة الخادم والواجهة معًا (خدمة واحدة)          | إلزامية (للنشر)
  Resend        | إرسال إشعارات البريد الإلكتروني                    | اختيارية
  Google Cloud  | إنشاء نماذج التسجيل ومزامنة الاستجابات             | اختيارية

مهم جدًا:
  - المنصة تعمل بالكامل بدون Resend وبدون Google. في هذه الحالة:
      * كل الإشعارات تظهر داخل المنصة فقط (جرس الإشعارات)، ولا يُرسل أي بريد.
        الرسائل تُسجَّل بحالة "disabled" ولا تدّعي المنصة أنها أُرسلت.
      * صفحة «القبول والتسجيل» تعمل لكن لا يمكن إنشاء نماذج Google أو مزامنتها.
  - كل الخدمات المذكورة لها خطط مجانية كافية. لا تفعّل أي خطة مدفوعة.
  - الاستثناء الوحيد الذي قد يكلّف مالًا: Resend يحتاج نطاقًا (domain) تملكه.
    شراء نطاق ليس مجانيًا عادة (تقريبًا 10 دولارات سنويًا). هذا قرارك أنت؛
    بدون نطاق يبقى البريد معطّلًا وتبقى الإشعارات داخل المنصة.


=====================================================================================
  1) Supabase — قاعدة البيانات
=====================================================================================

-------------------------------------------------------------------------------------
  1.1  الحصول على رابط الاتصال الصحيح (DATABASE_URL)
-------------------------------------------------------------------------------------

  1. افتح https://supabase.com/dashboard وسجّل الدخول.
  2. اختر مشروع الملتقى.
  3. اضغط زر «Connect» في الشريط العلوي للمشروع.
     (في بعض الواجهات القديمة: Project Settings ← Database ← Connection string)
  4. اختر تبويب «Connection String» ثم النوع «URI».
  5. اختر «Session pooler» (وليس Direct connection وليس Transaction pooler).
     سيظهر رابط بهذا الشكل:

       postgresql://postgres.xxxxxxxxxxxx:[YOUR-PASSWORD]@aws-1-xx-xxxx-x.pooler.supabase.com:5432/postgres

  6. استبدل [YOUR-PASSWORD] بكلمة مرور قاعدة البيانات (احذف الأقواس المربعة أيضًا).

  لماذا Session pooler بالتحديد؟
    - Direct connection (db.xxxx.supabase.co) يعمل عبر IPv6 فقط، وخطة Render
      المجانية لا تدعم IPv6 ← سيفشل الاتصال.
    - Transaction pooler (المنفذ 6543) لا يدعم الأقفال على مستوى الجلسة
      (advisory locks) التي يستخدمها المشروع في الترحيلات والمهام المجدولة.
    - Session pooler (المنفذ 5432) يدعم IPv4 والجلسات ← هو الصحيح.

  إن نسيت كلمة مرور قاعدة البيانات:
    Project Settings ← Database ← «Reset database password».
    تنبيه: بعد تغييرها يجب تحديث DATABASE_URL في Render وفي server/.env.

  إن احتوت كلمة المرور رموزًا خاصة مثل  @ # / : ? %  يجب ترميزها (URL-encode):
     @ ← %40     # ← %23     / ← %2F     : ← %3A     ? ← %3F     % ← %25
  الأسهل: اختر كلمة مرور من حروف وأرقام فقط.

  SSL: الكود يفعّل SSL تلقائيًا إذا احتوى الرابط على "supabase" أو "pooler"
  أو كانت البيئة production. لا تحتاج لإضافة ?sslmode=require.

-------------------------------------------------------------------------------------
  1.2  أين تضع DATABASE_URL
-------------------------------------------------------------------------------------

  - على Render: Service ← Environment ← DATABASE_URL (انظر القسم 2).
  - محليًا: في ملف server/.env (انسخه من .env.example).
    ملف .env مُدرج في .gitignore فلن يُرفع إلى GitHub. لا تضعه في أي ملف آخر.

  تحذير مهم: إذا كان server/.env على جهازك يشير إلى قاعدة Supabase الحقيقية، فإن
  تشغيل «npm run dev» أو «npm run migrate» محليًا سيعمل على البيانات الحقيقية.
  (الاختبارات «npm test» لا تلمس Supabase أبدًا — تستخدم قاعدة مؤقتة على جهازك.)

-------------------------------------------------------------------------------------
  1.3  تطبيق ترحيلات قاعدة البيانات (Migrations) بأمان
-------------------------------------------------------------------------------------

  ما الذي سيُطبَّق؟
    - database/schema.sql: الهيكل الأساسي (آمن لإعادة التشغيل).
    - database/migrations/001_platform_enhancements.sql: الإضافات الجديدة
      (جداول وأعمدة جديدة فقط — لا يحذف أي جدول أو بيانات).
    - كل ترحيل يُنفَّذ مرة واحدة فقط داخل transaction ويُسجَّل في جدول
      schema_migrations. إن فشل أي جزء يُلغى الترحيل كله ولا تتغير البيانات.

  الخطوة 1 — خذ نسخة احتياطية أولًا (إلزامي قبل أول ترحيل على بيانات حقيقية):

    الخطة المجانية في Supabase لا توفر نسخًا احتياطية قابلة للتنزيل، لذلك:

    الطريقة أ (موصى بها) — pg_dump:
      1. ثبّت أدوات PostgreSQL على جهازك (https://www.postgresql.org/download/)
         بإصدار مساوٍ أو أحدث من إصدار Supabase
         (تجده في Project Settings ← Infrastructure أو بتشغيل: select version();).
      2. في الطرفية:
           pg_dump "postgresql://postgres.xxxx:PASSWORD@....pooler.supabase.com:5432/postgres" -Fc -f misk-backup-2026-11-19.dump
      3. احفظ الملف في مكان آمن خارج مجلد المشروع (لا ترفعه إلى GitHub).

    الطريقة ب — تصدير الجداول المهمة يدويًا:
      Supabase ← Table Editor ← اختر الجدول ← زر Export ← CSV
      (users، supervisors، students، appointments على الأقل).

  الخطوة 2 — طبّق الترحيل (اختر طريقة واحدة):

    الطريقة أ (تلقائية عند النشر على Render):
      أمر البناء في render.yaml هو  npm run render-build  وهو يشغّل بالترتيب:
        تثبيت الخادم ← بناء الواجهة ← npm run migrate
      أي أن الترحيل يُطبَّق تلقائيًا مع كل نشر. إن فشل الترحيل يفشل النشر
      ويبقى الإصدار القديم يعمل.

    الطريقة ب (يدويًا من جهازك):
      1. تأكد أن server/.env يحتوي DATABASE_URL الصحيح.
      2. من جذر المشروع:
           npm run migrate
      3. النتيجة المتوقعة:
           ✅ تم تطبيق 1 ترحيل            (أول مرة)
           ✅ قاعدة البيانات محدّثة — لا ترحيلات جديدة   (المرات التالية)

  الخطوة 3 — تحقق:
    Supabase ← SQL Editor ← نفّذ:
        select * from schema_migrations order by applied_at;
    يجب أن يظهر سطر باسم 001_platform_enhancements.sql.

-------------------------------------------------------------------------------------
  1.4  إعداد Supabase Cron (المهام المجدولة)
-------------------------------------------------------------------------------------

  لماذا؟
    خادم Render المجاني «ينام» بعد 15 دقيقة بدون زيارات، فلا يمكن الاعتماد على
    مؤقتات داخل الخادم. Supabase Cron يستدعي الرابط
        POST  <رابط موقعك>/api/cron/tick
    كل ساعة (عند الدقيقة 7). الطلب يوقظ الخادم إن كان نائمًا ثم يُنفّذ:
      - متابعة اكتمال السجلات (التذكيرات والتحذيرات)
      - توليد تقارير الأداء كل 14 يومًا
      - مزامنة نماذج Google (إن كانت مربوطة)
      - نشر الإعلانات المجدولة
      - إرسال رسائل البريد المتأخرة/المعاد محاولتها
    المهام «تعويضية»: إن فاتت ساعة تُنجز ما فات في المرة التالية، ولا تكرر شيئًا.
    (يوجد أيضًا مجدول داخلي كل 15 دقيقة أثناء استيقاظ الخادم، لكنه مساعد فقط.)

  المتطلب المسبق: متغير CRON_SECRET مضبوط على Render (انظر القسم 2). بدونه يرد
  الخادم على /api/cron/tick بالخطأ 503 «CRON_SECRET غير مضبوط».

  الخطوات:
    1. Supabase ← Database ← Extensions:
         ابحث عن pg_cron وفعّله.
         ابحث عن pg_net وفعّله.
       (Vault مفعّل افتراضيًا في Supabase باسم supabase_vault.)
    2. انسخ قيمة CRON_SECRET من Render:
         Render ← خدمتك ← Environment ← CRON_SECRET ← زر العين لإظهارها ← انسخها.
    3. افتح الملف database/supabase_cron.sql في IntelliJ وانسخ محتواه كاملًا.
    4. Supabase ← SQL Editor ← New query ← الصق المحتوى.
    5. داخل محرر Supabase (وليس في الملف داخل المشروع) استبدل:
         <CRON_SECRET>  ← بالقيمة التي نسختها من Render
         <APP_URL>      ← برابط خدمتك على Render بدون شرطة / في النهاية
                          مثال: https://masak-quran-forum.onrender.com
    6. اضغط Run.
    7. لا تحفظ القيم الحقيقية في ملف database/supabase_cron.sql داخل المشروع،
       حتى لا يُرفع السر إلى GitHub. السر يُخزَّن مشفرًا في Supabase Vault.

  التحقق (بعد ساعة تقريبًا، أو بعد الدقيقة 7 من الساعة التالية):
    في SQL Editor:
      select * from cron.job_run_details
      where jobid = (select jobid from cron.job where jobname = 'mq-tick')
      order by start_time desc limit 10;

      select id, status_code, error_msg, created
      from net._http_response order by created desc limit 10;

    النتيجة الصحيحة: status_code = 200 (أو 202 إذا كانت مهمة سابقة ما زالت تعمل).
    401 ← السر في Vault لا يطابق CRON_SECRET على Render.
    503 ← CRON_SECRET غير مضبوط على Render أو أقصر من 24 حرفًا.
    ومن داخل المنصة: «متابعة السجلات» ← تبويب «سجل التشغيل» يُظهر كل تشغيل.

  تحديث السر أو الرابط لاحقًا (في SQL Editor):
    select vault.update_secret((select id from vault.secrets where name = 'mq_cron_secret'), 'NEW_SECRET_VALUE');
    select vault.update_secret((select id from vault.secrets where name = 'mq_app_url'), 'https://new-url.onrender.com');

  2) Render — الاستضافة ومتغيرات البيئة
=====================================================================================

  ملف render.yaml في جذر المشروع يعرّف خدمة ويب واحدة:
    name: masak-quran-forum   plan: free   region: frankfurt
    buildCommand: npm run render-build     startCommand: npm start
    healthCheckPath: /api/health

-------------------------------------------------------------------------------------
  2.1  الحالة أ: الخدمة غير موجودة بعد ← إنشاء عبر Blueprint
-------------------------------------------------------------------------------------

  1. ارفع المشروع إلى GitHub (تأكد أن .env غير مرفوع — هو في .gitignore).
  2. افتح https://dashboard.render.com
  3. New ← Blueprint.
  4. اربط حساب GitHub واختر مستودع المشروع.
  5. يقرأ Render ملف render.yaml ويعرض الخدمة. سيطلب منك إدخال المتغيرات
     المعلَّمة sync: false وهي:
       DATABASE_URL, ADMIN_PASSWORD, RESEND_API_KEY, EMAIL_FROM,
       GOOGLE_CLIENT_ID, GOOGLE_CLIENT_SECRET
     - DATABASE_URL و ADMIN_PASSWORD: إلزاميان الآن.
     - الباقي: اتركه فارغًا الآن إن لم تجهّز Resend/Google بعد، وأضفه لاحقًا.
  6. اضغط Apply / Deploy Blueprint.
  7. المتغيرات المعلَّمة generateValue: true (JWT_SECRET, CREDENTIALS_KEY, CRON_SECRET)
     يولّدها Render تلقائيًا بقيم عشوائية قوية.

-------------------------------------------------------------------------------------
  2.2  الحالة ب: الخدمة موجودة مسبقًا ← إضافة المتغيرات الجديدة يدويًا
-------------------------------------------------------------------------------------

  1. https://dashboard.render.com ← اختر خدمة masak-quran-forum.
  2. من القائمة الجانبية: Environment.
  3. Add Environment Variable لكل متغير جديد غير موجود (انظر القسم 5).
     الجديدة في هذا التحديث:
       CRON_SECRET, EMAIL_NOTIFICATIONS_ENABLED, RESEND_API_KEY, EMAIL_FROM,
       EMAIL_REPLY_TO, GOOGLE_CLIENT_ID, GOOGLE_CLIENT_SECRET
     لتوليد CRON_SECRET يدويًا (إن لم يولّده Render) شغّل على جهازك:
       node -e "console.log(require('crypto').randomBytes(32).toString('hex'))"
  4. اضغط Save Changes. اختر «Save, rebuild, and deploy» إن ظهر الخيار.
  5. إن لم يبدأ نشر تلقائيًا: أعلى صفحة الخدمة ← Manual Deploy ← Deploy latest commit.

  ملاحظة: إن كانت الخدمة مرتبطة بـ Blueprint فقد يضيف Render المتغيرات الجديدة من
  render.yaml عند مزامنة الـ Blueprint (Blueprints ← اختر الـ Blueprint ← Sync).
  تأكد في كل الأحوال من صفحة Environment أن كل متغير موجود.

  2.4  التأكد من أن كل شيء يعمل بعد النشر
-------------------------------------------------------------------------------------

  1. Logs (سجل الخدمة) أثناء البناء يجب أن يحتوي:
       ✅ تم تطبيق 1 ترحيل      أو      ✅ قاعدة البيانات محدّثة — لا ترحيلات جديدة
  2. افتح في المتصفح:  https://<اسم-خدمتك>.onrender.com/api/health
       {"status":"ok", ...}          ← قاعدة البيانات متصلة
       {"status":"db_unavailable"}   ← مشكلة في DATABASE_URL (انظر القسم 6)
  3. سجّل الدخول كمسؤول ← القائمة الجانبية ← «النظام والحساب» ← «الإعدادات»
     ← تبويب «التكاملات (البريد و Google)»:
       - البريد الإلكتروني (Resend): «يعمل» أو «غير مُفعّل» مع قائمة بما ينقص بالضبط.
       - Google Forms و Google Sheets: «مربوط» أو «غير مربوط».
  4. «متابعة السجلات» ← «سجل التشغيل»: يجب أن تظهر تشغيلات بمصدر supabase-cron
     بعد إعداد Cron.

  ملاحظة أداء: render.yaml يضع الخدمة في منطقة frankfurt، بينما رابط Supabase الحالي
  في منطقة ap-southeast-2 (سيدني). هذا يعمل لكنه يضيف تأخيرًا في كل استعلام.
  ليس خطأ ولا يحتاج إجراء الآن؛ فقط للعلم.


=====================================================================================
  3) Resend — إرسال البريد الإلكتروني
=====================================================================================

  كيف يعمل في الكود:
    - الإرسال عبر Resend HTTPS API (https://api.resend.com/emails) — لا SMTP ولا
      كلمات مرور Gmail.
    - اسم المرسل ثابت في الكود: «إدارة ملتقى المسك القرآني».
    - الرد (Reply-To) يذهب إلى EMAIL_REPLY_TO (الافتراضي misk.quran26@gmail.com).
    - البريد يُرسل فقط إلى عناوين مؤكَّدة (المستخدم ضغط رابط التأكيد).
    - كل رسالة تُحفظ أولًا في جدول email_outbox ثم تُرسل في الخلفية مع إعادة
      المحاولة حتى 6 مرات عند الأخطاء المؤقتة، ومنع التكرار (Idempotency-Key).
    - الكود يرفض EMAIL_FROM إذا كان على بريد مجاني
      (gmail, googlemail, yahoo, hotmail, outlook, live, icloud, aol, proton).
      أي: لا يمكن الإرسال «من» misk.quran26@gmail.com — لكن يمكن «الرد إليه».

-------------------------------------------------------------------------------------
  3.1  إنشاء حساب Resend
-------------------------------------------------------------------------------------

  1. افتح https://resend.com ← Sign Up.
  2. سجّل (يمكن باستخدام misk.quran26@gmail.com). لا تحتاج بطاقة دفع للخطة المجانية.
  3. أكّد بريدك من الرسالة التي تصلك.

-------------------------------------------------------------------------------------
  3.2  إضافة نطاق وتوثيقه (Domain) — خطوة يدوية إلزامية لإرسال البريد
-------------------------------------------------------------------------------------

  تحتاج نطاقًا تملكه (مثال: misk-quran.org). يُفضَّل استخدام نطاق فرعي للإرسال
  مثل mail.misk-quran.org حتى لا يتأثر بريد النطاق الرئيسي.

  1. Resend ← القائمة الجانبية ← Domains ← Add Domain.
  2. اكتب النطاق (مثال: mail.misk-quran.org) واختر المنطقة (Region) الأقرب، ثم Add.
  3. يعرض Resend سجلات DNS يجب إضافتها حرفيًا عند مزوّد النطاق
     (Namecheap / GoDaddy / Cloudflare ...):
       - MX  و  TXT (SPF)  على الاسم الذي يعرضه Resend (عادة يبدأ بـ send)
       - TXT (DKIM) باسم resend._domainkey
     انسخ Name و Value كما هما تمامًا.
  4. موصى به لتقليل الوصول إلى Spam — أضف سجل DMARC:
       Type: TXT     Name: _dmarc     Value: v=DMARC1; p=none;
  5. ارجع إلى Resend ← Domains ← اضغط Verify DNS Records.
     قد يستغرق التوثيق من دقائق إلى 48 ساعة. انتظر حتى تصبح الحالة Verified.

-------------------------------------------------------------------------------------
  3.3  إنشاء مفتاح API
-------------------------------------------------------------------------------------

  1. Resend ← API Keys ← Create API Key.
  2. Name: misk-render
     Permission: Sending access (يكفي ولا يعطي صلاحيات إدارية)
     Domain: اختر النطاق الموثّق.
  3. اضغط Add. سيظهر المفتاح مرة واحدة فقط ويبدأ بـ re_
  4. انسخه فورًا وضعه في Render (الخطوة التالية). لا تحفظه في أي ملف داخل المشروع.

-------------------------------------------------------------------------------------
  3.4  ضبط المتغيرات على Render
-------------------------------------------------------------------------------------

  Render ← خدمتك ← Environment:
    RESEND_API_KEY              = re_xxxxxxxxxxxxxxxxxxxx   (المفتاح الذي نسخته)
    EMAIL_FROM                  = noreply@mail.misk-quran.org
                                  (أي عنوان على النطاق الموثّق — لا تضع اسمًا هنا،

-------------------------------------------------------------------------------------
  3.5  اختبار الإرسال
-------------------------------------------------------------------------------------

  1. سجّل الدخول كمسؤول ← «النظام والحساب» ← «الإعدادات» ← «التكاملات (البريد و Google)».
  2. قسم «البريد الإلكتروني (Resend)» يجب أن يُظهر «يعمل» مع:
       المرسل: noreply@... • الرد إلى: misk.quran26@gmail.com
     إن ظهر «غير مُفعّل» فستظهر تحته قائمة بما ينقص بالضبط (مثلًا: RESEND_API_KEY غير مضبوط).
  3. اكتب بريدًا للاختبار في خانة المستلم ← «إرسال رسالة تجريبية».
     (حد أقصى 5 رسائل تجريبية في الساعة.)
  4. الجدول تحت الزر يُظهر الحالة: sent = أُرسلت، failed = فشلت مع سبب الخطأ.
     يمكن الضغط على «إعادة» لإعادة محاولة رسالة فاشلة.
  5. تحقق من صندوق الوارد (وصندوق Spam). وفي Resend ← Emails يظهر سجل كل رسالة.
  6. اختبار حقيقي: أضف مشرفًا ببريد تملكه ← يجب أن تصله رسالة «تأكيد البريد»
     تحتوي رابطًا يبدأ برابط موقعك على Render.

-------------------------------------------------------------------------------------
  3.6  حدود الخطة المجانية وتقليل الوصول إلى Spam
-------------------------------------------------------------------------------------

  حدود الخطة المجانية (وقت كتابة الدليل — تأكد من https://resend.com/pricing):
    - 3,000 رسالة شهريًا، و100 رسالة يوميًا.
    - نطاق واحد.
  الكود يحترم حد السرعة (رسالة كل 0.6 ثانية) ويعيد المحاولة تلقائيًا عند الخطأ 429.
  إن تجاوزت 100 رسالة في يوم (مثلًا إعلان لعدد كبير من المشرفين)، تُؤجَّل البقية
  وتُعاد محاولتها تلقائيًا، وقد يفشل بعضها بعد 6 محاولات ← يمكن إعادتها يدويًا من
  جدول الرسائل في الإعدادات.

  لتقليل الوصول إلى Spam:
    1. وثّق SPF و DKIM وأضف DMARC (القسم 3.2).
    2. استخدم عنوان إرسال ثابتًا على النطاق نفسه (مثل noreply@mail...).
    3. اطلب من المشرفين إضافة عنوان الإرسال إلى جهات الاتصال وتعليم أول رسالة
       بأنها «ليست رسالة غير مرغوب فيها».
    4. لا ترسل إعلانات كثيرة متتالية في وقت قصير.
    5. الكود يرسل نسخة HTML ونسخة نص عادي لكل رسالة، وهذا يساعد على التسليم.

  4) Google — نماذج التسجيل (Forms) وجداول الاستجابات (Sheets)
=====================================================================================

  كيف يعمل في الكود:
    - المسؤول يربط حساب Google الخاص بالملتقى (misk.quran26@gmail.com) مرة واحدة
      عبر OAuth. يُحفظ refresh token مشفرًا في قاعدة البيانات (جدول integration_secrets)
      بمفتاح CREDENTIALS_KEY.
    - الصلاحيات (scopes) المطلوبة فعليًا في الكود:
        openid
        email
        https://www.googleapis.com/auth/forms.body
        https://www.googleapis.com/auth/forms.responses.readonly
        https://www.googleapis.com/auth/drive.file
      (drive.file = الوصول فقط للملفات التي أنشأها التطبيق نفسه، وليس كل Drive.)
    - الواجهات البرمجية التي يستدعيها الكود فعليًا:

    - رابط العودة (Redirect URI) في الكود:

         - يُنشأ Google Form في Drive حساب الملتقى بحقول القبول (الاسم، الجنس،

    4. انسخ «رابط التسجيل» وشاركه مع المتقدمين.

  المزامنة:
    - تلقائيًا: كل ساعة عبر Supabase Cron، وكل 15 دقيقة أثناء استيقاظ الخادم.
    - يدويًا: «نماذج التسجيل» ← «مزامنة الآن».
    - كل استجابة تُستورد مرة واحدة فقط، وتُضاف كصف في الـ Sheet الخاص.
    - ملاحظة تقنية: Google Forms API لا يسمح بربط جدول الاستجابات الأصلي برمجيًا،
      لذلك ينشئ التطبيق Sheet خاصًا به ويضيف الصفوف إليه بنفسه. هذا الجدول ليس
      «Responses sheet» الذي تراه داخل Google Forms — وهو طبيعي.
    - «إيقاف المزامنة» يوقف استيراد نموذج معيّن دون حذفه.

  3. في المنصة: «القبول والتسجيل» ← «نماذج التسجيل» ← «مزامنة الآن».
     يجب أن تظهر رسالة «استُورد 1 طلب جديد» ويظهر الطلب في الجدول بحالة «جديد».
  4. افتح «جدول الاستجابات» من نافذة النماذج ← يجب أن ترى الصف نفسه.
  5. اضغط على الطلب ← غيّر حالته إلى «قيد المراجعة» ← أضف ملاحظة.
  6. «قبول» ← اختر مشرفًا مناسبًا ← تأكيد. يجب أن يظهر الطالب في صفحة «الطلاب».
  7. أرسل استجابة ثانية بنفس الاسم والهاتف ← بعد المزامنة تظهر بعلامة «مكرر؟».
  8. جرّب «رفض» على طلب آخر.
  9. احذف بيانات الطلاب التجريبيين بعد الانتهاء (حذف ناعم من صفحة الطالب).
  10. مشرف التسجيل: أنشئ حسابًا من «المشرفون» ← «إضافة مشرف» ← النوع
      «مشرف تسجيل وقبول»، وسجّل الدخول به وتأكد أنه يرى القبول والإعلانات
      والرسائل فقط.

  EMAIL_NOTIFICATIONS_ENABLED                    [اختياري] [غير سري]
    false (الافتراضي) = لا إرسال، إشعارات داخل المنصة فقط.
    true = إرسال فعلي (فقط بعد توثيق النطاق ووضع المفتاح).
    التحقق: الإعدادات ← التكاملات ← البريد = «يعمل».

  RESEND_API_KEY                                 [مطلوب للبريد] [سري]
    المصدر: Resend ← API Keys (القسم 3.3). يبدأ بـ re_
    التحقق: «إرسال رسالة تجريبية» تنجح بحالة sent.

  EMAIL_FROM                                     [مطلوب للبريد] [غير سري]
    عنوان على نطاق موثّق في Resend، مثل noreply@mail.your-domain.com.
    لا يُقبل Gmail أو أي بريد مجاني (الكود يرفضه ويُظهر السبب في الإعدادات).

  EMAIL_REPLY_TO                                 [اختياري] [غير سري]
    القيمة: misk.quran26@gmail.com (الافتراضي في الكود حتى لو لم يُضبط).
    التحقق: الرد على أي رسالة من المنصة يذهب إلى هذا البريد.

  RESEND_API_BASE                                [لا تضبطه] [غير سري]
    موجود في الكود لأغراض الاختبار فقط (الافتراضي https://api.resend.com).

  GOOGLE_CLIENT_ID                               [مطلوب لـ Google] [غير سري نسبيًا]
    المصدر: Google Cloud ← Credentials ← OAuth client (القسم 4.4).
    لا تنشره علنًا رغم أنه ليس سرًا بالمعنى الصارم.

  GOOGLE_CLIENT_SECRET                           [مطلوب لـ Google] [سري]

    التحقق: زر «ربط حساب Google» يعود إلى الإعدادات برسالة نجاح.


=====================================================================================
  6) استكشاف الأخطاء وإصلاحها
=====================================================================================

  [Google] Error 401: invalid_client  /  "The OAuth client was not found"
    السبب: GOOGLE_CLIENT_ID أو GOOGLE_CLIENT_SECRET خطأ أو فيه مسافة زائدة.
    الحل: انسخهما من جديد من Google Cloud ← Credentials، احذف أي مسافات،
          احفظ في Render وأعد النشر.

  [Google] Error 400: redirect_uri_mismatch
    السبب: الرابط الذي يرسله التطبيق لا يطابق Authorized redirect URIs.
    الحل:
      1. في صفحة الخطأ اضغط «error details» وانسخ redirect_uri الظاهر.
      2. أضفه حرفيًا في Google Cloud ← Credentials ← العميل ← Authorized redirect URIs.
      3. تأكد: https وليس http، لا / في النهاية، نفس اسم النطاق.
      4. قد يحتاج التغيير عدة دقائق ليسري.

  [Google] Error 403: access_denied  /  "has not completed the Google verification process"
    السبب: التطبيق في وضع Testing والحساب ليس ضمن Test users.
    الحل: أضف misk.quran26@gmail.com إلى Test users، أو انشر التطبيق إلى
          Production (القسم 4.3 الخطوة 7).

  [Google] بعد أسبوع تقريبًا: «رفض Google الطلب: invalid_grant»
    السبب: التطبيق ما زال في وضع Testing فانتهت صلاحية الربط بعد 7 أيام، أو أُلغيت
           الصلاحية من حساب Google، أو تغيّر CREDENTIALS_KEY.
    الحل: انشر التطبيق إلى Production ثم «إعادة الربط» من الإعدادات.

  [Google] «لم يُرجع Google رمز التحديث. أزل صلاحية التطبيق من حسابك ثم أعد الربط.»
    الحل: https://myaccount.google.com/permissions ← اختر التطبيق ← Remove access
          ← ثم «ربط حساب Google» من جديد.

  [Google] «خطأ من Google: ... has not been used in project ... or it is disabled»
    السبب: Google Forms API أو Google Sheets API غير مفعّل.
    الحل: فعّله (القسم 4.2)، انتظر دقيقتين، ثم أعد المحاولة.

  [Google] «Request had insufficient authentication scopes» / PERMISSION_DENIED
    السبب: لم تُمنح كل الصلاحيات عند الربط.
    الحل: أزل صلاحية التطبيق من الحساب (الرابط أعلاه) ثم أعد الربط ووافق على كل
          المربعات.

  [Google] بعد الربط تعود إلى صفحة الدخول أو تظهر رسالة state
    السبب: فتحت الموقع من نطاق مختلف عن رابط العودة، أو انتهت جلستك، أو مرّت
           أكثر من 10 دقائق بين الضغط والعودة.
    الحل: افتح الموقع من نفس رابط Render المسجّل، سجّل الدخول، وأعد الضغط فورًا.

  [Google] «تعذر نشر النموذج تلقائيًا»
    الحل: «نماذج التسجيل» ← «تحرير النموذج» ← زر Publish في Google Forms.

  [Google] زر «إنشاء نموذج تسجيل» معطّل
    السبب: Google غير مربوط. انظر الإعدادات ← التكاملات.

  [Resend] الإعدادات تقول: «EMAIL_FROM يجب أن يكون على نطاق موثّق...»
    السبب: EMAIL_FROM على Gmail أو بريد مجاني.
    الحل: استخدم عنوانًا على نطاقك الموثّق.

  [Resend] فشل بخطأ 403 / "The ... domain is not verified"
    السبب: النطاق في Resend ليس Verified بعد، أو EMAIL_FROM على نطاق آخر.
    الحل: Resend ← Domains ← Verify DNS Records، وتأكد أن نطاق EMAIL_FROM هو نفسه.

  [Resend] فشل بخطأ 401 / "API key is invalid"
    السبب: RESEND_API_KEY خطأ أو محذوف أو فيه مسافة.
    الحل: أنشئ مفتاحًا جديدًا (القسم 3.3)، ضعه في Render، أعد النشر.

  [Resend] خطأ 429 / تأخر الرسائل
    السبب: تجاوز حد السرعة أو الحد اليومي (100 رسالة).
    الحل: لا شيء؛ الكود يعيد المحاولة تلقائيًا. الفاشلة نهائيًا تُعاد يدويًا بزر «إعادة».

  [Resend] الرسائل تصل إلى Spam
    الحل: القسم 3.6 (DMARC، عنوان ثابت، إضافة المرسل لجهات الاتصال).

  [Resend] الحالة «disabled» لكل الرسائل
    السبب: EMAIL_NOTIFICATIONS_ENABLED ليس true، أو ينقص مفتاح/مرسل.
    الحل: الإعدادات ← التكاملات تعرض ما ينقص بالضبط. الرسائل القديمة بحالة
          disabled يمكن إعادتها بزر «إعادة» بعد الإعداد.

  [عام] الخادم لا يبدأ: «DATABASE_URL غير مضبوط» / «JWT_SECRET مطلوب» / «CREDENTIALS_KEY مطلوب»
    الحل: أضف المتغير الناقص في Render ← Environment، وتأكد أن JWT_SECRET 32 حرفًا
          فأكثر، ثم أعد النشر.

  [قاعدة البيانات] timeout / ETIMEDOUT / ENETUNREACH / connect ECONNREFUSED
    الأسباب والحلول:
      - تستخدم Direct connection (IPv6) ← استخدم Session pooler (القسم 1.1).
      - مشروع Supabase متوقف (Paused) بعد عدم نشاط ← Supabase Dashboard ←
        Restore project.
      - كلمة مرور فيها رموز غير مرمّزة ← رمّزها أو غيّرها لحروف وأرقام.

  [قاعدة البيانات] password authentication failed for user "postgres.xxxx"
    الحل: أعد تعيين كلمة مرور قاعدة البيانات في Supabase وحدّث DATABASE_URL.

  [قاعدة البيانات] too many connections / MaxClientsInSessionMode
    الحل: ضع DB_POOL_MAX=5 على Render، وتأكد أنك لا تشغّل نسخة محلية متصلة بنفس
          القاعدة في نفس الوقت.

  [Render] فشل البناء (Build failed)
    افتح Logs واقرأ آخر الأسطر:
      - «❌ فشل الترحيل: ...» ← خطأ في قاعدة البيانات؛ لم يتغير شيء (transaction).
        انسخ الرسالة وتحقق من DATABASE_URL.
      - npm ERR! ← تأكد أن NODE_VERSION = 22 وأن package-lock.json مرفوع.
      - تأكد أن Build Command = npm run render-build و Start Command = npm start.

  [Render] Health check failed / الخدمة لا تصبح Live
    الحل: افتح /api/health. إن كان db_unavailable فالمشكلة في DATABASE_URL.
          وراجع Logs لأي رسالة خطأ عند البدء.

  [Render] الموقع بطيء جدًا أول مرة
    طبيعي في الخطة المجانية: الخادم ينام بعد 15 دقيقة ويحتاج 30–60 ثانية للاستيقاظ.

  [Cron] status_code 401 في net._http_response
    السر في Vault لا يطابق CRON_SECRET. حدّثه بأمر vault.update_secret (القسم 1.4).

  [Cron] status_code 503 أو خطأ CRON_DISABLED
    CRON_SECRET غير مضبوط على Render أو أقصر من 24 حرفًا.

  [Cron] لا توجد أي سجلات في cron.job_run_details
    تأكد أن pg_cron مفعّل وأن select * from cron.job; يُظهر mq-tick.

  [Cron] timeout في net._http_response
    الخادم احتاج وقتًا للاستيقاظ أكثر من 120 ثانية (نادر). المهام تعويضية وستُنجز
    في التشغيل التالي.


=====================================================================================
  7) ما هو غير مكتمل أو يحتاج خطوة يدوية منك
=====================================================================================

  1. لم يُختبر الإرسال الحقيقي عبر Resend ولا الربط الحقيقي مع Google.
     الاختبارات الآلية (34 اختبارًا) تستخدم استجابات محاكاة لهاتين الخدمتين.
     بعد إعدادهما نفّذ اختبارات القسمين 3.5 و 4.8 يدويًا.
  2. Resend يحتاج نطاقًا تملكه وتوثّقه (قد يكلّف شراء النطاق — قرارك).
  3. Google: يجب إنشاء OAuth Client، ونشر التطبيق إلى Production، وربط الحساب
     يدويًا من صفحة الإعدادات.
  4. Supabase Cron: لم يُنفَّذ ملف database/supabase_cron.sql بعد — يجب تنفيذه
     يدويًا في SQL Editor (القسم 1.4).
  5. ترحيل قاعدة البيانات 001_platform_enhancements.sql لم يُطبَّق على قاعدة
     الإنتاج بعد. سيُطبَّق تلقائيًا في أول نشر على Render، أو يدويًا بـ
     npm run migrate. خذ نسخة احتياطية أولًا (القسم 1.3).
  6. التغييرات الحالية في المشروع لم تُرفع إلى GitHub بعد (لا يوجد commit).
     Render ينشر من GitHub، فيجب رفعها أولًا.
  7. الطلاب ليس لديهم حسابات دخول في النظام، فلا يصلهم بريد من المنصة؛ البريد
     للمشرفين ومشرفي التسجيل والمسؤول فقط.
  8. التجربة المحلية لربط Google: رابط العودة المحلي هو
     http://localhost:4000/api/google/oauth/callback ويعود إلى صفحة الإعدادات على
     المنفذ 4000، وهي تُخدَم فقط إن بنيت الواجهة أولًا (npm run build).
     الأسهل: اختبر ربط Google على Render مباشرة.
